# Local vision worker

This worker reads newline-delimited JSON from stdin and writes protocol JSON only to stdout. Diagnostics go to stderr. It does not download weights or send frames to a cloud service.

## YouTube sources

`probe_youtube` resolves one public video and decodes a JPEG for idle scene setup. `analyze_youtube` uses the configured local detector and a 500 ms sampling target. Each preview notification contains source/session/frame IDs, elapsed source time and encoded image dimensions; the corresponding analysis event uses the same decoded image and timestamp. The web viewer pairs these identities before displaying detections.

The resolver dependencies are pinned to the tested yt-dlp nightly `2026.10.10.233141.dev0` and its matching `yt-dlp-ejs==0.8.0` in `pyproject.toml` and `setup-yolo26.ps1`. The nightly is pinned because the installed stable build was refused while this tested build resolved and decoded both supplied public live sources anonymously. Existing environments need both packages installed in the interpreter selected by `VISION_PYTHON`. YouTube support requires Node.js 22 or newer on PATH; the resolver enables the discovered local Node executable explicitly. The matching EJS scripts stay local and remote components remain disabled. See the [official EJS setup guide](https://github.com/yt-dlp/yt-dlp/wiki/EJS) and [nightly channel guidance](https://github.com/yt-dlp/yt-dlp#update). The resolver accepts single-video watch, live and youtu.be URLs, drops playlists, selects at most 1080p, and keeps signed media URLs in memory. Public anonymous streams are supported when YouTube grants access; account cookies and authentication are unavailable. Missing components, timeouts and anonymous sign-in/bot gates have distinct safe messages, with explicit access gates taking precedence over generic challenge warnings. Live reconnect attempts are bounded. Temporary JPEGs are bounded per source/session; they are previews, not a recording archive.

Live acquisition keeps only the newest decoded frame while inference targets two samples per second. Reads follow the reported native frame rate so buffered HLS segments cannot be consumed in an instant. A periodic deadline corrects small scheduling delays and resets after a larger stall; unknown frame rates use a bounded fallback with a quality note. Recorded videos use media positions for sampling. Neither a video's publication time nor the source's creation time supplies a recording-date reference. A video that plays on its public YouTube page can still refuse direct media access from this PC.

## Setup

### macOS

On macOS 14 or newer with Node.js 22+ and Python 3.12 or 3.13, run `npm ci` at the repository root followed by `npm run setup:mac`. The setup script checks prerequisites and the machine architecture, creates the isolated `apps/vision/.venv-worker`, installs pinned dependencies, downloads the OpenCV Zoo YOLOX-S ONNX file, and verifies its SHA-256. On Apple Silicon it also installs PyTorch 2.10.0, torchvision 0.25.0 and Ultralytics 8.4.175, then downloads the official YOLO26 Medium checkpoint and verifies SHA-256 `401cea9ab23ad19246ff7744859816bc599f350e93c9dd30367b6f0a0745d0b7`. These PyTorch versions have official macOS arm64 wheels for Python 3.12 and 3.13, listed in the [official PyTorch version matrix](https://pytorch.org/get-started/previous-versions/). The setup uses ordinary macOS/PyPI wheels and never selects the Windows CUDA index.

The Apple Silicon runtime requests MPS only when the installed PyTorch reports both `torch.backends.mps.is_built()` and `is_available()`; otherwise it selects CPU. Set `VISION_DEVICE=cpu` in `.env` to force CPU inference if an MPS operator is unsupported, or `VISION_DEVICE=auto` to restore automatic selection. Other values fail configuration with a clear error. Runtime inference errors remain visible instead of being converted into detections. The code has unit coverage for CUDA, available/unavailable MPS, CPU override and invalid settings, but no physical Mac was available for an end-to-end MPS or throughput test. Do not assume the Windows RTX 3080 timings apply to a Mac.

Current official PyTorch release wheels target macOS arm64, so Intel Macs select the OpenCV Zoo YOLOX-S CPU path with ONNX Runtime 1.23.2, which publishes macOS x86_64 wheels in its [release files](https://pypi.org/project/onnxruntime/1.23.2/). This path is suitable as a basic CPU fallback and has no GPU throughput claim. The pinned OpenCV wheel currently requires macOS 14 or newer on both architectures ([wheel details](https://pypi.org/project/opencv-python-headless/5.0.0.93/)). The setup does not install Python, Node.js or Homebrew; if it reports a missing prerequisite, install that tool and rerun `npm run setup:mac`.

The setup creates a profile in `.env` only when that file does not exist. If you already have `.env`, preserve it and review its `VISION_*` values yourself. `npm run dev` starts the local dashboard and API after setup. More detailed startup and detector notes below describe the Windows runtime where explicitly stated.

Use Python 3.12 on Windows. `pwsh -File apps/vision/setup.ps1` provisions the CPU fallback in `apps/vision/.venv-worker`, with pinned NumPy 2.5.4, OpenCV 5.0.0.93 and ONNX Runtime 1.31.0. It explicitly downloads the checksum-verified OpenCV Zoo YOLOX-S model only during setup. The default `py` launcher selects Python 3.12; a specific interpreter can be supplied with `-PythonExe`, for example `C:\Path\To\Python312\python.exe`. This CPU setup script does not install GPU packages.

`pwsh -File apps/vision/setup-yolo26.ps1` provisions the evaluated GPU detector in the separate `.venv-yolo26` environment, with PyTorch 2.10.0 / torchvision 0.25.0 CUDA 12.8 and Ultralytics 8.4.175. It downloads the official `yolo26m.pt` and verifies SHA-256 `401cea9ab23ad19246ff7744859816bc599f350e93c9dd30367b6f0a0745d0b7`. Configuration and package caches stay local to the workspace; usage sync/integrations are disabled. The optional RF-DETR setup is `setup-rfdetr.ps1`, with `-IncludeLarge` for the current Large 2026 weights. These are explicit setup actions; normal startup uses existing local files. Actual GPU inference was verified on this PC's RTX 3080 Laptop with 16 GiB memory; capacity across several cameras remains unverified.

The setup model is YOLOX-S (640x640 COCO), provided by OpenCV Zoo under Apache 2.0. Setup downloads the immutable Hugging Face revision `c5c37f2482d90a975d2dc6a2d491f307cf41bd2d` from [the model file](https://huggingface.co/opencv/object_detection_yolox/resolve/c5c37f2482d90a975d2dc6a2d491f307cf41bd2d/object_detection_yolox_2022nov.onnx) and verifies SHA-256 `c5c2d13e59ae883e6af3b45daea64af4833a4951c92d116ec270d9ddbe998063`. The adapter applies its exported grid/stride decode and objectness-times-class-score calculation. Other local models can be configured when they use a compatible raw YOLO ONNX output: YOLOv8 style `[1,84,N]` or `[1,N,84]`, YOLOv5 style with objectness, or postprocessed `[N,6]` rows. Configure their path explicitly; setup does not replace the default model silently.

The ONNX adapter depends only on ONNX Runtime, NumPy, and OpenCV. All detector paths use the same lightweight IoU/motion tracker. RF-DETR core Medium/Large models use Apache-2.0; YOLO26 uses Ultralytics 8.4.175 and its official Medium COCO checkpoint under AGPL-3.0, with an Enterprise licensing alternative. Detector environments are separate; setup does not install packages globally or silently select an application backend.

YOLO26 configuration is opt-in through `VISION_DETECTOR_BACKEND=yolo26`, a local `VISION_MODEL_PATH`, and the matching Python environment in `VISION_PYTHON`. A per-session `inputSize` or `nms` config overrides its environment fallback. The adapter accepts only 640, 960, or 1280 input sizes; events and health report the effective size, NMS path, model, and actual device. Ultralytics initialization and prediction diagnostics are routed to stderr so stdout remains the worker's JSON-lines protocol.

GPU inference has been exercised locally on Windows, but performance depends on hardware, frame size, and detector configuration. Those results do not establish a real-time or multi-camera capacity guarantee. No native Mac performance result is claimed.

The COCO model emits broad `car`, `motorcycle`, `bus`, and `truck` classes (the pipeline filters non-vehicle classes). It cannot reliably infer ownership or vehicle subtypes from appearance, so the worker reports its supported broad classes rather than implying unsupported detail.

Color is a coarse image-based HSV estimate from the central body portion of each detection box, not a trained paint classifier. It can return `white`, `gray`, `black`, `red`, `orange`, `yellow`, `green`, `blue`, `purple`, `pink`, or `unknown`. Small or mixed crops remain `unknown`. Optional `colorSupportRatio` reports the fraction of usable crop pixels in the winning color bin; it is a heuristic support share, not a calibrated probability or accuracy score. `colorMethod: "hsv_estimate"` identifies the source. Road/background pixels, shadows, compression, and overhead viewpoints can still make the estimate wrong.

## Protocol

Each input line is one JSON object. Commands include `readiness`, `health`, `configure`, `start`, `process_frame`, `analyze_upload`, `analyze_stream`, `stop`, and `shutdown`. `process_frame` takes a local `framePath` and `sourceTimeMs`. Upload and stream analyses run asynchronously and emit `job_started`, frame-level `analysis` events, then `job_complete` or `error`; the command reader remains available while they run. GPU inference is serialized. Every source session owns an independent tracker and line-crossing state; use a fresh `sessionId` for each rerun.

`VISION_DETECTION_MODE=auto` (the default) runs overlapping full-frame tiles plus configured line detail when the sampled frame's longest side exceeds 1280 pixels. Each sampled frame is spatially covered end to end; the extra line crops preserve detail around saved counting gates. On 3840×2160 input, six 1408×1188 tiles overlap at the seams. Detections are remapped to full-frame normalized coordinates and globally deduplicated. `auto` retains a broad 0.12-margin gate pass and adds a tighter 0.05-margin pass, split into overlapping crops targeting 640×640 pixels, with a global cap of eight fine patches. If that cap would omit any configured gate region, the remaining region is kept as one whole crop. The included 4K scene uses twelve inference regions per sampled frame: six full-frame tiles, two broad gate crops, and four fine patches. In a bounded three-frame check, these patches improved selected near-line vehicle-center matches from 13/17 to 15/17, at about 0.20–0.27 seconds of additional CPU time per sampled frame; this is not a general accuracy guarantee. Below the threshold, `auto` uses one full-frame inference pass.

`VISION_DETECTION_MODE=tiled` runs full-frame tiles without the extra gate crops. `line_roi` explicitly limits inference to up to eight configured line regions. `full` resizes the complete frame to the model input in one pass; small distant vehicles can disappear at 4K. `VISION_LINE_ROI_MARGIN` controls the normalized margin around each configured line for line-region analysis (default `0.12`, clamped to `0.05`–`0.25`). The worker reports the actual inference-region count and spatial scope in each event's quality notes. Every mode still samples video frames at `sampleEveryMs`: the API passes 500 ms for new upload sessions (2 FPS), while direct streams retain the worker's 1000 ms default. Sampling follows available source-frame timestamps, so actual intervals can be slightly longer. Gap notes flag intervals above 1.5 times the configured interval. Full-frame tile coverage applies to each sampled frame, not every decoded frame or every instant between samples. Tracks expire by source time after `max(1000 ms, sampleEveryMs × (max_missed + 1))` (6,500 ms with the current 500 ms sampling and 12-miss setting). A backward source-clock jump clears active matches while keeping IDs monotonic within that source session. A narrowly gated high-overlap vehicle-class flicker can retain a track only when the match is mutually unique; each detection keeps its own predicted class and attributes. IDs remain session-local and do not guarantee physical identity.

For YOLO26 tiled frames, a pair of tall, overlapping bus/truck tile predictions can trigger one additional whole-frame prediction. Only a uniquely matched anchor and a coherent, bounded cluster with crop-seam support can fuse those fragments before tracking. Cross-class interior matches, conflicting anchors and unsupported neighboring boxes remain separate. Event notes distinguish an applied fusion from an unsuccessful probe, and region counts include the extra pass. Crop-edge tolerance is 1.5% of the tile dimension. These rules reduce selected duplicate fragments but do not guarantee perfect detections or full-video accuracy.

High-resolution analysis can perform multiple overlapping image tiles and optional crops near saved counting lines. A narrowly scoped filter removes near-identical cross-class boxes at IoU ≥0.985 while retaining distinct overlapping vehicles. As with any visual detector, false positives and missed vehicles remain possible.

For new analyzed frames, the worker can stage an exact decoded-frame JPEG alongside the event identity for API evidence pinning; staging is bounded to four frames per source/session and each JPEG is capped at 4 MiB. Older uploaded-video events may be re-decoded from the retained local asset only when timestamp and dimensions verify within 1 ms; otherwise the frame is reported unavailable rather than substituting a player image. This is JPEG evidence of analyzed pixels, not lossless source-container data.

Frame detections now include every real model observation at the configured confidence threshold. A detection gets a `trackId` only after the local tracker accepts or matches it; observations without confirmed identity omit that optional field. Line crossings are emitted only from active tracked objects. These observation boxes are not themselves a distinct-vehicle count, and sampled events do not claim validated counting accuracy.

Crossing anchors use the midpoint of a vehicle box's bottom edge as a ground-contact proxy. A 2.5 second per-track/per-line recross debounce suppresses rapid side flips caused by detection jitter; each source session resets this state.

Scene geometry matches the shared API contract: `{zones:[{id,name,polygon:[{x,y}]}],countingLines:[{id,name,start:{x,y},end:{x,y},directionLabels:[string,string]}]}`. Geometry and bounding boxes are normalized to `[0,1]`. Events contain vehicle detections, line crossings, processing quality, source timestamps, and frame dimensions. Sampling gaps are reported and do not imply full-video coverage. Speed is not estimated because no camera calibration is available.

An explicit fixture detector may be injected by unit tests only. Production mode never substitutes fabricated detections when model or runtime setup fails.
